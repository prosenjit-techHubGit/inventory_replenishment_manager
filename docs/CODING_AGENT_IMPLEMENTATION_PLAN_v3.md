# Inventory Replenishment & Purchase Order Management
## Detailed Implementation Plan for a Coding Agent

## 1. Objective
Build a process-driven procurement application using:

- **Frontend:** React + TypeScript
- **Backend:** Spring Boot / Java
- **Orchestration:** Camunda 8 SaaS
- **Database:** PostgreSQL
- **AI:** Pluggable recommendation provider behind a Spring interface
- **Build:** Maven for backend, npm for frontend

The implementation must preserve a critical business boundary: **Replenishment Recommendation and Create Purchase Order are two separate Camunda processes.**

Do not collapse them into one BPMN model.

---

## 2. Core Business Flow

### 2.1 Process 1: Replenishment Recommendation
This process is always system initiated.

```text
Scheduled Timer
    -> Check Replenishment Requirement
    -> Replenishment Needed?
        -> No: End
        -> Yes: Create AI Recommendation
                 -> Review Recommendation [User Task]
                 -> Accepted?
                    -> No: End / Revision path
                    -> Yes: Invoke Create Purchase Order process
                            with prepopulated PO data
```

### 2.2 Process 2: Create Purchase Order
This is the main transaction process and must support two initiation paths.

#### Automated path
```text
Accepted Replenishment Recommendation
    -> Start Create Purchase Order
    -> Receive prepopulated PO data
    -> Submit PO
```

#### Manual path
```text
User selects Create Purchase Order
    -> React displays Create PO form
    -> User enters PO data
    -> Backend starts Create Purchase Order process
    -> Submit PO
```

Both paths then converge:

```text
Submit PO
    -> Determine Approval Route [DMN]
    -> Review PO [User Task]
    -> Supplier Confirmation [User Task]
    -> Release / Track Shipment
    -> Create GRN [User Task]
    -> Update Inventory
    -> End
```

### Non-negotiable design rule
The manual route must **not** run through the replenishment or recommendation process.

The automated route must **not** require the user to re-enter PO fields already generated by the accepted recommendation.

## 7. Camunda Process Model 1

Process ID:

```text
replenishment-recommendation
```

### BPMN steps

1. Timer Start Event
2. Check Replenishment Requirement - service task
3. Replenishment Required? - exclusive gateway
4. Create Recommendation - service task/job worker representing AI agent activity
5. Review Recommendation - user task
6. Recommendation Accepted? - exclusive gateway
7. Start/Create Purchase Order - use an explicit process-to-process invocation pattern supported by the selected Camunda model
8. End

### Check replenishment worker
Suggested job type:

```text
check-replenishment
```

Responsibilities:

- Load inventory item.
- Read on-hand quantity.
- Read reorder level.
- Read open purchase quantity.
- Decide whether recommendation processing should continue.
- Return only required workflow variables.

Suggested variables:

```json
{
  "itemId": "ITEM-100",
  "onHandQuantity": 18,
  "reorderLevel": 25,
  "openPurchaseQuantity": 0,
  "replenishmentRequired": true
}
```

### Recommendation worker
Suggested job type:

```text
create-recommendation
```

This is the explicitly marked AI-agent step.

Responsibilities:

- Load inventory context.
- Load eligible suppliers.
- Construct structured recommendation request.
- Invoke `RecommendationProvider`.
- Validate response.
- Persist Recommendation.
- Return recommendation variables to Camunda.

AI output must contain:

```json
{
  "recommendedQuantity": 80,
  "supplierId": "SUP-001",
  "targetDeliveryDate": "YYYY-MM-DD",
  "riskLevel": "LOW",
  "rationale": "..."
}
```

Validate:

- quantity > 0
- supplier exists and is active
- date is populated
- risk enum is valid
- rationale is not blank

If AI invocation or validation fails, do not terminate the business process permanently. Route to a manual recommendation fallback or create a recoverable workflow error path.

### Recommendation Review task
React page must display:

- item
- current stock
- reorder level
- recommendation quantity
- recommended supplier
- target delivery date
- risk
- rationale

Actions:

```text
Accept
Modify and Accept
Reject
```

When modifying, validate edited values before task completion.

### Accepted recommendation handoff
Build a dedicated mapper:

```text
RecommendationToPurchaseOrderMapper
```

Map at minimum:

```text
recommendationId
itemId
quantity
supplierId
requiredDeliveryDate
supplierRisk
recommendationRationale
initiationType = REPLENISHMENT
```

The Create PO process must receive these fields as prepopulated process data.

## 8. Camunda Process Model 2

Process ID:

```text
create-purchase-order
```

### Required logical stages

```text
Start
 -> PO Data Ready
 -> Submit PO
 -> Determine Approval Route
 -> Review PO
 -> Supplier Confirmation
 -> Release PO
 -> Track Shipment
 -> Create GRN
 -> Update Inventory
 -> End
```

### Automated start
Input comes from Process 1.

Set:

```text
initiationType = REPLENISHMENT
```

The process receives prepopulated values and does not invoke the manual Create PO form.

### Manual start
React starts this path after the user completes the Create Purchase Order form.

Set:

```text
initiationType = MANUAL
```

The backend validates the form, creates a business PO record as appropriate for the chosen persistence approach, and starts the Camunda process with the submitted variables.


- Procurement approval for every PO.
- Finance approval when PO value exceeds a configurable threshold.

## 17. Recommendation Provider Abstraction

Do not call an LLM SDK directly from a Camunda worker class.

Define:

```java
public interface RecommendationProvider {
    RecommendationResponse recommend(RecommendationRequest request);
}
```

Worker flow:

```text
Camunda Worker
   -> RecommendationApplicationService
       -> RecommendationProvider
       -> validate output
       -> persist recommendation
       -> map process variables
```

Provide a deterministic `MockRecommendationProvider` first so the end-to-end process can be built before the real AI connection.

Use configuration/profile selection to swap providers.

## 23. Error Handling

### Business errors
Model predictable business outcomes in BPMN where useful:

```text

Recommendation rejected
PO rejected
Supplier rejected
Partial receipt
```

### Technical failures
Examples:

```text
AI endpoint unavailable
Database unavailable
Unexpected worker exception
Malformed AI response
```

For workers:

- log correlation identifiers
- avoid swallowing exceptions
- configure sensible retries
- ensure idempotency
- provide actionable failure messages

### AI fallback
If recommendation generation repeatedly fails:

```text
Create Recommendation
    -> Technical / validation failure
    -> Manual Recommendation Task
    -> Review Recommendation
```

The process must remain usable without AI.

## 29. Coding Standards

### Backend

- Prefer constructor injection.
- Keep controllers thin.
- Keep Camunda workers thin.
- Put business logic in application/domain services.
- Use DTOs at REST boundaries.
- Do not expose JPA entities directly.
- Centralize exception-to-HTTP mapping.
- Make integration operations idempotent where retries are possible.
- Use enums for bounded status values.
- Avoid magic strings for process/job/task identifiers; centralize identifiers.

### Frontend

- Type all API contracts.
- Centralize HTTP client behaviour.
- Provide consistent loading/error states.
- Do not duplicate backend business validation logic beyond UX validation.
- Keep process-specific routing in a task-screen registry/mapping.
- Avoid embedding Camunda credentials or confidential configuration into frontend builds.

### BPMN

- Give every activity a business-readable name.
- Give technical elements stable IDs.
- Define explicit variable mappings between processes where supported/appropriate.
- Use timers for time-dependent behaviour.
- Use DMN for routing decisions that are business rules.

# 35. Approval Contract

## 35.1 Approval policy

Approvals are **sequential and conditional**, not parallel.

Order:

```text
1. Procurement Manager     ALWAYS
2. Finance Approver        CONDITIONAL
3. Supply Chain Manager    CONDITIONAL
```

Exactly one approval is required from each required role. A PO is fully approved only when every required approval task has outcome `APPROVED`.

Do not create one generic `Review PO` task for all approvers.

The BPMN must contain distinct user tasks or an explicitly modeled sequential approval subprocess so the audit trail identifies the required role and outcome.

Recommended BPMN shape:

```text
Determine Approval Route [DMN]
    -> Procurement Manager Approval
    -> Finance Required?
       -> Yes -> Finance Approval
    -> Supply Chain Required?
       -> Yes -> Supply Chain Approval
    -> Supplier Confirmation
```

## 35.2 DMN output

Prefer explicit booleans instead of an unstructured list:

```json
{
  "procurementApprovalRequired": true,
  "financeApprovalRequired": true,
  "supplyChainApprovalRequired": false
}
```

Procurement approval is always `true` in v1.

Finance is required when the configured PO-value threshold is exceeded.

Supply Chain is required when any configured supply-chain condition is true, including the use-case conditions of urgent request, critical item, or high supplier risk.

## 35.3 Assignment

Candidate groups:

```text
PROCUREMENT_MANAGER
FINANCE_APPROVER
SUPPLY_CHAIN_MANAGER
```

At runtime, one authorized user claims and completes each required role task.

The custom React/Spring task application is responsible for enforcing who may claim/complete tasks. Do not assume engine assignment alone is an application authorization check.

## 35.4 Approval outcomes

Each approval task supports:

```text
APPROVE
RETURN_FOR_REVISION
REJECT
```

### APPROVE
Record:

```text
role
approverUserId
outcome = APPROVED
completedAt
comment
```

Then proceed to the next required role.

### RETURN_FOR_REVISION
Route to one `Revise Purchase Order` user task assigned to the Procurement Buyer.

The buyer may edit:

```text
quantity
supplier
unitPrice
requiredDeliveryDate
urgency
businessJustification
```

After revision:

1. Recalculate PO value.
2. Recalculate supplier-risk input if supplier changed.
3. Re-run the Approval DMN.
4. Restart the approval chain from Procurement Manager.
5. Prior approval records remain immutable audit history, but they do **not** count toward approval of the revised version.
6. Increment `poRevision`.

### REJECT
Set PO status to `REJECTED`, record rejection reason, skip Supplier Confirmation, and end the Create PO process with business outcome `REJECTED`.

Do not automatically re-open a rejected PO in v1.

## 35.5 Approval persistence

Add `purchase_order_approval`:

```text
id PK
purchase_order_id FK
po_revision
approval_role
approver_user_id nullable until completion
outcome
comment
created_at
completed_at nullable
```

Uniqueness:

```text
(purchase_order_id, po_revision, approval_role)
```

The row represents the approval requirement for that PO revision. If audit requirements need every attempt rather than current requirement state, add a separate immutable approval-event table; do not overload the uniqueness rule.


```text
PLANNED -> DISPATCHED

IN_TRANSIT -> DELAYED
DELAYED -> IN_TRANSIT
```

Every shipment belongs to one PO.

```text
UNIQUE (purchase_order_id, supplier_shipment_reference)
```

## 37.4 Goods Receipt

A PO can have **multiple goods receipts**.

Each GoodsReceipt is an immutable receipt event after creation/confirmation:

```text
id
purchase_order_id
shipment_id nullable
receipt_number
received_quantity
accepted_quantity
rejected_quantity
receipt_date
notes
created_at
```

Constraints:

```text
received_quantity > 0
accepted_quantity >= 0
rejected_quantity >= 0
accepted_quantity + rejected_quantity <= received_quantity
UNIQUE (purchase_order_id, receipt_number)
```

Do not store a mutable `remainingQuantity` as a source of truth.

Derive:

```text
cumulativeReceivedQuantity = SUM(received_quantity)
cumulativeAcceptedQuantity = SUM(accepted_quantity)
remainingQuantity = orderedQuantity - cumulativeAcceptedQuantity
```

Prevent cumulative accepted quantity from exceeding ordered quantity.

PO receipt status:

```text
remainingQuantity > 0 and cumulativeAcceptedQuantity > 0 -> PARTIALLY_RECEIVED
remainingQuantity = 0 -> RECEIVED
```

# 38. Manual PO Creation Consistency and Idempotency

## 38.1 Request contract

Manual process creation endpoint:

```text
POST /api/v1/purchase-orders
```

Require HTTP header:

```text
Idempotency-Key: <client-generated UUID>
```

React generates one UUID when the user begins a submission attempt and reuses it for retries of that same submission. A changed business request must use a new key.

Persist an `idempotency_request` record:

```text
idempotency_key PK
operation
request_hash
status
resource_id nullable
process_instance_key nullable
response_json nullable
last_error nullable
created_at
updated_at
```

Statuses:

```text
IN_PROGRESS
COMPLETED
RETRYABLE_FAILURE
FAILED
```

If the same key is received with a different request hash, return HTTP 409.

If the same key is `COMPLETED`, return the original materialized response without starting another process.

## 38.2 PO creation/startup sequence

Within one local database transaction:

1. Insert/lock `idempotency_request`.
2. Allocate `purchaseOrderId` and `poNumber`.
3. Persist PO as `DRAFT`.
4. Commit.

Then start Camunda using a deterministic business correlation value:

```text
poRequestId = idempotencyKey
```

On Camunda start success:

1. Persist returned `processInstanceKey`.
2. Set PO to `IN_PREPARATION`.
3. Set idempotency record to `COMPLETED`.
4. Return HTTP 201.

On ambiguous timeout or technical failure:

1. Do **not** create a new PO.
2. Set PO to `START_FAILED` only when startup has not been confirmed.
3. Set idempotency request to `RETRYABLE_FAILURE`.
4. Recovery uses the same PO and same `poRequestId`.

The retry/recovery component must first determine whether a process instance for the deterministic correlation/request identifier already exists. If it exists, link the existing instance to the PO rather than starting another one. If no instance exists, retry process creation.

This is an application-level recovery contract; do not assume a database transaction can atomically encompass Camunda SaaS.

## 38.3 Automated handoff idempotency

The automated handoff originates from a BPMN Call Activity, so Camunda controls child-process creation for that process path.

The application must still enforce:

```text
recommendationId -> at most one PurchaseOrder
```

When the child process first creates/initializes its business PO record, use a deterministic `poRequestId` derived from the recommendation, for example:

```text
REC:<recommendationId>
```

A worker retry must load the existing PO rather than insert a second PO.

# 39. Replenishment Scheduling and Concurrency Contract

## 39.1 Schedule model

Use **one global batch timer process**, not one timer per inventory item.

For the capstone, configure one scheduled Replenishment Recommendation process instance to run at a configurable cron/time interval.

The scheduled instance queries candidate inventory items and processes each candidate using a BPMN multi-instance subprocess or an equivalent bounded iteration. Do not create N independent timers for N items.

Configuration example:

```text
replenishment.schedule=<externalized cron/schedule>
```

Do not hard-code a production schedule in BPMN or Java for the capstone.

## 39.2 Replenishment formula

For candidate detection, calculate:

```text
projectedAvailable = onHandQuantity + openPurchaseQuantity
replenishmentRequired = projectedAvailable < reorderLevel
```

`openPurchaseQuantity` means quantities on active, not-completed purchase orders that are still expected to arrive.

This quantity is considered in the recommendation calculation. It is **not** a stock reservation and must not increase physical `onHandQuantity` before accepted receipt.

## 39.3 Concurrency guard

Before creating a recommendation for an item, acquire an application-level item replenishment lock/claim in PostgreSQL.

Use a table such as:

```text
replenishment_claim
item_id PK
run_id
status
claimed_at
expires_at
```

Claim insertion/update must be atomic.

Only one active claim per `item_id` is allowed.

Before recommendation creation, re-read the item and active open-order quantities inside the claim-protected section. This second check prevents an earlier candidate snapshot from creating a stale recommendation after another order or receipt changed supply.

Release/complete the claim when:

- no replenishment is required after re-check;
- a recommendation is created;
- the item encounters a terminal run failure;
- an expired claim is recovered.

Additionally, do not create another active recommendation when the same item already has `PENDING_REVIEW` or `ACCEPTED` recommendation coverage that has not yet been represented by the current open-order calculation.

## 39.4 Receipt/order concurrency

Inventory updates must use optimistic locking (`@Version`) or a database row lock for the inventory row.

Goods-receipt completion must update inventory and register receipt application effects in one local transaction.

The inventory update worker must have an idempotency/apply-once key based on `goodsReceiptId`, so Camunda worker retries cannot increment stock twice.

After a receipt or PO state change, future replenishment runs use fresh database state. Do not attempt to mutate an already approved recommendation automatically in v1.

## Scope

Implement:

```text

-> POST /api/v1/purchase-orders
```

## Acceptance criteria

### Happy path

- The form creates exactly one PO.
- Exactly one Camunda process instance is linked to the PO.
- PO number is displayed consistently in React, PostgreSQL, logs, and Camunda variables.
- PO reaches Procurement Manager Approval.

### Duplicate HTTP submission

When the same `Idempotency-Key` and same request body is POSTed twice:

- only one PO exists;
- only one process instance exists;
- the second call returns the established resource/result.

### Conflicting idempotency reuse

When the same key is used with a different request body:

- return HTTP 409;
- do not modify the existing PO;
- do not start another process.

### Camunda start transient failure

When PO persistence succeeds but process startup cannot be confirmed:

- PO remains recoverable as `START_FAILED`/pending recovery;
- retry does not insert a second PO;
- recovery uses the same `poRequestId`;
- once a process is confirmed, the PO is linked and continues.

### Client timeout after server success

When the server starts the process successfully but the HTTP client retries because it did not receive the response:

- the repeated request resolves through the same idempotency record;
- no duplicate process is intentionally started;
- backend reconciliation links the already-created process if startup outcome had been ambiguous.

### Approval authorization

- only a user authorized for `PROCUREMENT_MANAGER` may complete the Procurement Manager Approval through the React/backend application;
- unauthorized completion returns 403 and leaves task/process state unchanged.

### Return for revision

- Procurement Manager may return the PO;
- PO enters `REVISION_REQUIRED`;
- Procurement Buyer edits the PO;
- `poRevision` increments;
- approval restarts for the new revision.

### Reject

- Procurement Manager rejection sets PO to `REJECTED`;
- Supplier Confirmation is never created for that PO.

# 44. v3 Corrections — THESE SUPERSEDE CONFLICTING v1/v2 TEXT

Sections 44-50 are the final binding contracts. If any earlier section conflicts with these sections, **sections 44-50 win**.

## 44.1 Final process-handoff decision: asynchronous message start, not Call Activity

Do **not** use a Call Activity for the Recommendation -> Create Purchase Order handoff.

The v2 Call Activity decision is superseded.

Reason: the replenishment process is a scheduled batch-style process and should not remain active until the long-running PO fulfillment lifecycle completes.

Final pattern:

```text
PROCESS 1 — REPLENISHMENT RECOMMENDATION
Scheduled batch
 -> Check item
 -> Create recommendation
 -> Review recommendation
 -> Accepted
 -> Prepare PO Handoff [worker]
      - create PO record
      - create outbox event
 -> End Process 1

OUTBOX PUBLISHER
 -> Publish CREATE_PURCHASE_ORDER message

PROCESS 2 — CREATE PURCHASE ORDER
Message Start Event: CREATE_PURCHASE_ORDER
 -> Prepare PO
 -> Submit for Approval
 -> ... fulfillment lifecycle ...
```

Therefore scheduled recommendation runs may overlap in time, but completed recommendation instances do **not** stay open waiting for PO fulfillment. Concurrency is handled per inventory item using the replenishment-claim contract in section 49.

## 44.2 Camunda-supported start deduplication mechanism

Create Purchase Order must start from a **BPMN Message Start Event** named:

```text
CREATE_PURCHASE_ORDER
```

Publish with:

```text
correlationKey = poRequestId
messageId      = outboxEventId
```

`poRequestId` is stable for the business request:

```text
manual:         MANUAL:<idempotencyKey>
automated:      REC:<recommendationId>
```

Use a positive message TTL sufficient for normal outbox retries and deployment/transient availability. Externalize this value as configuration.

The application must not use a plain CreateProcessInstance retry loop for Create PO startup.

Camunda's message-start correlation key provides engine-side protection against creating another active instance for the same correlation key. The message ID provides message-publication idempotency for the message-delivery window.

Application idempotency remains necessary because engine-side active-instance protection is not a permanent business uniqueness constraint after process completion.

# 45. Unified PO Creation Contract

This section resolves the PO-creation timing conflict.

## 45.1 Rule

For **both manual and automated initiation**, create the persistent PurchaseOrder record **before** publishing the `CREATE_PURCHASE_ORDER` message.

Process 2 never creates the PO record.

Process 2 loads/validates the PO by `purchaseOrderId` supplied in the start message.

## 45.2 Manual initiation

Within one PostgreSQL transaction:

1. Validate `Idempotency-Key` and request hash.
2. Create/find `idempotency_request`.
3. Allocate `purchaseOrderId` and `poNumber`.
4. Persist PurchaseOrder with:
   - `initiationType = MANUAL`
   - `status = PENDING_PROCESS_START`
   - `poRequestId = MANUAL:<idempotencyKey>`
5. Persist one `process_start_outbox` row for `CREATE_PURCHASE_ORDER`.
6. Commit.

The HTTP request returns a resource representing accepted creation. Recommended initial response:

```text
202 Accepted
```

because process start is asynchronous through the outbox.

React polls/refreshes the returned PO resource, or the application can later add push updates.

## 45.3 Automated initiation after recommendation acceptance

The `Prepare PO Handoff` Camunda job worker performs one local PostgreSQL transaction:

1. Lock/load accepted Recommendation.
2. Derive `poRequestId = REC:<recommendationId>`.
3. Check for existing PO by `recommendationId` / `poRequestId`.
4. If absent, allocate `purchaseOrderId` and `poNumber`.
5. Persist PurchaseOrder with:
   - `initiationType = REPLENISHMENT`
   - recommendation-derived PO fields
   - `status = PENDING_PROCESS_START`
6. Persist one `process_start_outbox` row.
7. Commit.
8. Complete the Camunda worker using the existing/new PO identifiers.

On worker retry, return the existing PO rather than create another one.

When this worker completes, Process 1 may end. It does not wait for Process 2.

## 45.4 Process 2 message payload

Publish only stable identifiers and routing fields:

```json
{
  "purchaseOrderId": "uuid",
  "poNumber": "PO-2026-000001",
  "poRequestId": "REC:recommendation-id",
  "initiationType": "REPLENISHMENT",
  "recommendationId": "uuid-or-null"
}
```

Process 2 loads detailed PO data from PostgreSQL when needed rather than treating a large message payload as the business source of truth.

## 46.2 Publication behavior

A single logical outbox event uses a stable:

```text
messageId = process_start_outbox.id
```

Every retry of that outbox event republishes the same message name, correlation key, message ID, and business payload.

Do not generate a new message ID on retry.

After Camunda acknowledges publication, mark the event `PUBLISHED`.

If publication outcome is ambiguous, retain the same event and same message ID when retrying.

## 46.3 What is guaranteed

The application guarantees:

- one business PO per manual idempotency key;
- one business PO per accepted recommendation;
- one outbox event per `poRequestId`;
- retries reuse the same outbox message ID;
- downstream process logic is keyed by the immutable `purchaseOrderId` / `poRequestId`.

Do **not** claim that a distributed database + Camunda interaction is an atomic exactly-once transaction.

Use Camunda message-start idempotency plus database uniqueness and reconciliation to achieve effectively-once business behavior.

## 46.4 Duplicate-process reconciliation

Add a first automated step in Process 2:

```text
Register Process Start
```

The worker atomically updates PurchaseOrder only if `camundaProcessInstanceKey` is null.

Pseudo-contract:

```text
UPDATE purchase_order
SET camunda_process_instance_key = :currentProcessInstanceKey,
    status = 'IN_PREPARATION'
WHERE id = :purchaseOrderId
  AND camunda_process_instance_key IS NULL
```

If no row is updated:

- if the stored process instance key equals the current key: treat as idempotent retry;
- if a different process instance key is already stored: mark/report the current instance as a duplicate and take the modeled duplicate-start termination path before any business side effects.

This duplicate-detection path is a defensive reconciliation mechanism. It must not create another PO or execute approvals/fulfillment.

- never insert another PO/outbox row.

# 49. Final Replenishment Scheduling and Open-PO Calculation

## 49.1 Scheduling

Use one global scheduled batch process.

The batch instance discovers candidate item IDs and evaluates them independently. Long-running PO processes are not child Call Activities, so a scheduled batch is free to complete after its recommendation work is done.

Overlapping scheduled batch instances are tolerated at the batch level. **They must not concurrently create recommendations for the same item.** The per-item `replenishment_claim` is the business concurrency guard.

## 49.2 Incoming open purchase quantity

For an item, calculate incoming quantity per non-terminal PO as:

```text
remainingIncomingForPO = max(orderedQuantity - cumulativeAcceptedQuantity, 0)
```

Then:

```text
openPurchaseQuantity = SUM(remainingIncomingForPO)
```

Count only POs whose status indicates that future accepted supply is still expected:

```text
APPROVED
PENDING_SUPPLIER_CONFIRMATION
SUPPLIER_DATE_REVISED
SUPPLIER_CONFIRMED
RELEASED
IN_FULFILLMENT
PARTIALLY_RECEIVED
```

Do not count:

```text
DRAFT
PENDING_PROCESS_START
IN_PREPARATION
PENDING_APPROVAL
REVISION_REQUIRED
REJECTED
SUPPLIER_REJECTED
RECEIVED
COMPLETED
CANCELLED
START_FAILED
```

Rationale for v1: unapproved/draft POs are not committed future supply; rejected/cancelled/completed orders no longer represent outstanding incoming supply.

For a partially received PO, only the unaccepted remainder counts as incoming supply.

## 49.3 Projected supply formula

```text
cumulativeAcceptedQuantity = SUM(accepted goods receipts for the PO)
remainingIncomingForPO = orderedQuantity - cumulativeAcceptedQuantity
openPurchaseQuantity = SUM(remainingIncomingForPO for qualifying POs)
projectedAvailable = onHandQuantity + openPurchaseQuantity
replenishmentRequired = projectedAvailable < reorderLevel
```

Accepted receipt quantity must update `onHandQuantity` exactly once. Once accepted stock is reflected on hand, the same accepted quantity is subtracted from the PO's incoming amount by the formula above, avoiding double counting.

## 49.4 Per-item claim sequence

For each candidate item:

1. Atomically acquire/renew `replenishment_claim` for item.
2. Re-read inventory using fresh committed data.
3. Calculate qualifying open PO remainder using the formula above.
4. Check for an already-active recommendation for the same item.
5. Re-evaluate `replenishmentRequired`.
6. Create at most one new recommendation if required.
7. Complete/release claim.

Expired claims can be reclaimed using `expires_at`; reclaim must be atomic.
